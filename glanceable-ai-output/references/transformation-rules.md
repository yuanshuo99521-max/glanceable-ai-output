# 项目机器状态到用户判断的转换规则

本参考只用于 `project_status` 模式。重组普通 AI 回答或技术说明时读取 [answer-reframing.md](answer-reframing.md)，不要把 Gate、State 或完成度规则强加给非项目内容。

## 转换对象不是标签，而是影响

不要逐词翻译 `Gate`、`State`、`Artifact`、`Agent`、`Node` 或日志字段。先回答：

1. 这条信息描述什么对象。
2. 它当前证明了什么。
3. 它没有证明什么。
4. 它会改变哪个项目步骤、质量判断或下一动作。
5. 结论由哪个来源、时间和作用范围支持。

## 最小事实记录

转换前为每项决定性信息保留以下内部记录：

```text
source:
observed_at:
scope:
object_type:
raw_state:
project_effect:
verification_level:
acceptance_level:
uncertainty_or_conflict:
```

缺失字段写成未知，不从相邻对象补齐。

## 事实强度阶梯

以下层级必须分开表达，低层不能自动升级为高层：

```text
对象存在
  → 结构或内容完整
  → 技术检查通过
  → 领域、业务、科学或用户接受
  → 整体目标完成
```

对象存在只能支持存在性结论；测试通过只能支持被运行测试及其覆盖条件；正式接受需要独立的接受记录或用户确认。

## Gate

### 读取字段

- 条件或检查目的。
- 当前结果和时间。
- 结果适用的对象与版本。
- 未通过或未检查会影响的下一步。

### 转换规则

- `pass`：说明具体条件已通过；使用 `✅`，不得宣布整个项目完成。
- `pending`：说明检查尚未完成；通常使用 `⏳` 或 `❓`，只有关键动作因此无法继续时才另列 `⛔`。
- `fail`：解释失败对关键路径的影响；能继续时用 `⚠️`，不能继续时用 `⛔`。
- Gate 定义不明或结果与对象版本不匹配：使用 `❓`。

## State

### 转换规则

- 把状态码转换为项目中可验证的当前行为，不直接把状态码当作用户结论。
- `running` 只有在存在当前进程、近期心跳、持续输出或项目定义的等价活动证据时才映射为 `🔄`。
- 历史日志、陈旧快照或遗留锁文件不能单独证明仍在运行。
- `done` 只说明该状态机进入终态；还要检查终态定义、结果和接受边界。
- 状态所有者不明或多个来源给出不一致状态时使用 `❓`。

## Artifact

分别检查并表达：

- 是否存在。
- 是否完整。
- 是否经过技术验证。
- 是否获得领域、业务、科学或用户接受。

表达约束：

- 生成、完整、技术验证和接受状态必须分别表达。
- 已确认条件使用与其证据层级一致的 `✅`；未执行的后续检查使用 `⏳`，接受状态不明时使用 `❓`。
- 候选对象不得写成正式产物，必须保留候选限定。
- 路径存在但内容未读时，只能确认路径或对象存在。

## Agent

- Agent 只在责任、等待对象或当前执行证据影响判断时出现。
- 自报“完成”是一个来源，不是最终验收。
- 空闲、停止或失联不能解释任务为何结束，也不能证明成功。
- Agent 与状态所有者冲突时，展示来源冲突；不根据语气选择结论。
- 用户不需要恢复或审计时，可以隐藏内部 Agent 标识，只保留责任角色。

## Node

- 先说明用户可理解的工作步骤；内部名称只有在恢复、操作或审计需要时才在其后保留。
- Node 前进证明流程位置发生变化，不证明该节点产物正确或已接受。
- 前置条件未满足但节点已前进时，记录异常或来源冲突，不能自动修正叙述。
- 后继动作应同时给出对象和可验证结果。

## 日志、测试与检查

- 把退出码、错误和警告转换为对目标的影响。
- 合并同一根因的重复日志，避免按行数夸大严重度。
- 原始错误文本只在定位需要时放入 `🔎`，保留最小上下文，并先移除个人标识、主机信息和凭据值。
- 测试 PASS 只证明被运行的测试及其覆盖范围。
- 未运行、跳过、超时和没有采集结果是不同状态，不得合并为失败或通过。

## 时间与新鲜度

- 结论需要当前性时，检查时间戳、版本、分支或对象标识。
- 项目规则定义了陈旧阈值时按项目规则执行。
- 没有阈值时，不自创精确时限；说明“仅有历史记录”及其时间。
- 新来源不自动覆盖旧来源；只有项目所有权规则或可验证的继承关系才能确定优先级。

## 冲突、未知与推论

### 冲突

- 同时展示冲突双方的最小标识、时间和作用范围。
- 使用 `❓` 表示事实尚未确定。
- 如果冲突阻止发布、运行或接受，再用 `⛔` 说明被阻止的动作。

### 未知

- “没有找到”只能说明在已检查范围内未找到。
- 未读外部位置、无权限或无真实项目路径必须反映在来源覆盖状态中。
- 不把 `unknown` 改写为 `not started`、`failed` 或 `complete`。

### 推论

- 只有对决策有价值时才输出 `💡`。
- 明确使用“推测”“可能”“由此推断”等限定，并说明推论依据。
- 推论不得承担完成、阻塞或接受结论所需的证据职责。

## 下一步生成规则

下一步必须：

- 针对当前最高影响缺口。
- 包含动作和对象。
- 能判断是否完成；必要时写明检查或接受条件。
- 不虚构责任人、期限、权限或外部承诺。

下一步的最小语义结构为“动作 + 对象 + 可验证完成条件”。只有继续意愿、没有对象或无法判断完成的表述必须拒绝。

## 输出前语义检查

- 是否把存在写成完整、把技术 PASS 写成接受、把局部终态写成整体完成。
- 是否把历史 `running` 写成当前进行。
- 是否把风险、阻塞和未知混用。
- 是否暴露会改变结论的来源冲突、时间边界和覆盖缺口。
- 是否保留用户领域术语，并只对项目内部术语做必要桥接。
- 是否让下一步直接处理当前最高影响事项。
- 是否把普通 AI 回答误路由为项目状态，或为非项目内容虚构进行中、待处理和阻塞状态。
