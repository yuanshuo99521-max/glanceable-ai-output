# 固定视觉符号系统

## 封闭词典

| 符号 | 固定宏观语义 | 使用条件 |
|---|---|---|
| `📍` | 核心结论或当前位置 | 输出开头，用一句话概括最重要理解或当前整体状态 |
| `🎯` | 当前问题、目标或判断标准 | 用户要解决的问题、目标或验收条件需要显式说明 |
| `✅` | 已确认的事实、结果或已完成条件 | 当前范围内已有充分证据支持紧随其后的具体内容 |
| `🔄` | 正在进行 | 已启动，存在当前活动证据，尚未终结 |
| `⏳` | 尚未开始或排队等待 | 已知需要做，但尚未启动 |
| `⚠️` | 已确认的限制、问题或风险 | 影响理解、质量、时间或结果，但关键路径仍可继续 |
| `⛔` | 已确认的阻塞 | 不解除就无法执行关键下一步 |
| `❓` | 尚未确定或待决策 | 信息不足、来源冲突、方案或授权待定 |
| `💡` | 解释、发现或明确标注的推论 | 对理解或判断有价值，但需区分解释、事实和推论 |
| `➡️` | 可支持的下一步动作 | 输入或已核验事实支持的可执行、可判断动作 |
| `🔎` | 必要术语与依据 | 支持关键判断的术语、来源、检查和边界 |

## 固定顺序

只输出有内容的区块，并保持以下相对顺序：

```text
📍 → 🎯 → ✅ → 🔄 → ⏳ → ⚠️ → ⛔ → ❓ → 💡 → ➡️ → 🔎
```

`📍` 必须是第一个语义区块。只有内容支持可执行后续时才使用 `➡️`。关键结论存在争议、阻塞、输入边界或验收边界时必须使用 `🔎`。

## 模式使用规则

### `answer_reframe`

- 通常从 `📍` 开始，根据内容选用 `🎯`、`✅`、`⚠️`、`❓`、`💡`、`➡️` 和 `🔎`。
- `🔄` 与 `⏳` 只在输入确实描述任务或流程状态时使用。
- 不为普通概念解释虚构完成、进行、等待、阻塞或下一步。
- `REFRAMED_FROM_PROVIDED_INPUT` 下的外部事实断言不能因为被重写就升级为 `✅`；只能确认“原回答确实这样陈述”，不能确认该陈述为真。只有达到 `INDEPENDENTLY_VERIFIED` 边界的具体主张，或输入本身可直接证明的文本属性，才能使用 `✅`。

### `project_status`

- 继续使用全部状态符号及现有活动证据、完成层级和来源覆盖规则。
- Agent 结束、Gate PASS、Node 前进或 Artifact 存在都不能单独支持整体完成。

## 关键区分

### `⚠️` 与 `⛔`

- 仍可沿关键路径继续：`⚠️`。
- 关键下一步无法继续：`⛔`。
- 同一问题同时符合二者时只用 `⛔`。

### `❓` 与异常状态

- 尚不知道是否有问题：`❓`。
- 已确认有影响但可以继续：`⚠️`。
- 已确认阻止下一步：`⛔`。

### `⏳` 与 `🔄`

- 还没有当前活动证据：`⏳`。
- 已启动且仍有当前活动证据：`🔄`。
- 历史 `running`、陈旧心跳或旧日志不能支持 `🔄`。

### `✅` 的作用域

`✅` 只确认紧随其后的具体内容。

- 回答重组模式中，必须区分“输入明确陈述”和“已独立验证”；前者不能伪装成后者。
- 项目状态模式中，对象存在、内容完整、技术验证、领域或用户接受以及整体完成属于不同判断层级；确认其中一个不得升级其余层级。

## 组合规则

- 同一报告中不同证据层级必须分别判定，不得用单一符号合并。
- 普通解释可以只使用少量必要符号；没有状态内容时不得补齐状态区块。
- 未启动状态与阻止启动的条件具有不同语义，可以分别进入 `⏳` 和 `⛔`。
- 来源冲突及其阻止的关键动作具有不同语义，可以分别进入 `❓` 和 `⛔`。
- 已完成条件和正在执行的后续条件必须明确各自作用范围，不能写成同一对象的矛盾状态。

## 禁止用法

- 不引入 `🟢`、`🔴`、`❌`、`🚧`、`🟡` 等近义状态符号。
- 不用 `⚠️` 表示下一步。
- 不用 `❓` 表示已经确认的阻塞。
- 不用 `✅` 表示候选、估计或“看起来差不多”。
- 不用 `✅` 确认超出所读来源或接受记录支持范围的主张。
- 不把输入中未经核验的断言写成“已证实”或“客观事实”。
- 不用 `➡️` 补写原文和证据都不支持的建议。
- 不在每个列表项前重复状态 Emoji。

## 可访问性

- 每个符号必须配具体文字标题。
- 不依靠颜色传递状态。
- 一个区块标题最多一个主符号。
- 同一宏观语义跨报告保持相同符号；具体标题可以变化。
